# Recording findings

Each item cost a failed run. Read before writing or changing a flow.

1. Playwright video needs **Playwright's own ffmpeg** (`playwright install ffmpeg` → `~/.cache/ms-playwright/ffmpeg-<rev>`), not the system one. The install must use the same playwright-core version the MCP server runs.
2. Playwright MCP's `browser_run_code_unsafe` with `filename` only reads files under the **workspace roots** (project dir and `<project>/.playwright-mcp`). Flow scripts must be written into the project, not loaded from the skill directory.
3. Each `run_code` call runs in a **fresh VM context**, so `globalThis` does not persist between calls. State must ride on the `page` object, which does persist (see #13 for how the flow uses that).
4. A **fresh worktree's Vite dev server re-optimizes deps mid-session**, which leaves two React copies loaded and crashes the page (`Cannot read properties of null (reading 'useMemo')`), and can cause a login form to submit as a native GET before hydration. Fix: dry-run first (step 3) and `waitForLoadState('networkidle')` before interacting.
5. **Open a fresh browser context (or at least a new tab) per phase.** `page.on(...)` listeners and overlays accumulate on a reused page (the pill rendered twice).
6. **Don't trust HTTP status** with React Router single-fetch, which returns 200 with the real status inside the payload. Assert on UI state instead.
7. `gh pr edit --attach` needs gh **2.99+**. The machine used for the trial had 2.46.
8. Native video output: VP9 webm at 1280×720 and 25 fps. A 33 s clip is about 540 KB after an x264 crf 28 re-encode, far under GitHub's 10 MB free-plan limit.
9. **Mobile emulation works per phase without restarting the MCP.** Inside `browser_run_code_unsafe`, `page.context().browser().newContext({ viewport, deviceScaleFactor: 3, isMobile: true, hasTouch: true, userAgent })` gave innerWidth 390, DPR 3, `pointer: coarse`, mobile UA, and `page.screencast` was available (tested 2026-11-20, `@playwright/mcp@latest`, Chromium). Those numbers held, but the video was still wrong in a headed window: see #14.

10. **`freezedetect` misses small UI changes.** A counter ticking every 100 ms in a 390×844 frame reads as fully frozen even at −80 dB; at −90 dB it flickers. `mpdecimate` (8×8 block compare) catches it: use its kept-frame timestamps for tail trimming and the motion gate.
11. Playwright's screencast webm carries a real duration (`ffprobe format=duration` works) and is saved at the CSS viewport size, not × DPR.
12. **Frozen time is high even in good recordings.** The counter proof (23.5 s) was ~75 % frozen: chapter cards, banners and pauses change nothing. It still had 66–74 changed frames, against 1 for a blank recording. The motion gate sits at 95 % frozen so slow walkthroughs aren't re-recorded for nothing; the dry-run gate catches scenarios that silently did nothing.
13. **MCP echoes the full code of every `browser_run_code_unsafe` call**, `filename` runs included: a 110-line flow run 4 times put ~450 lines into the agent's context. A function stored on `page` in one call stays callable in later calls (its VM context lives on). So the harness (`harness.js`, ~100 lines) registers `page.__ba.run` once per run, each scenario file registers `page.__ba.<kind>`, and each phase is a one-line `page.__ba.run(page, kind, params)` call. The first real project run reloaded a 190-line flow 6 times (~1,100 lines); with the split, an edit re-echoes only the scenario. `require` and dynamic `import()` are unavailable in the VM, so a short call cannot read the file itself.
14. **Never record in a headed window.** Playwright MCP runs Chrome headed by default, and each new context there is a real window that the window manager sizes (Hyprland tiles it). The screencast records that window, not the emulated viewport: a 390×844 mobile video showed a ~1280-wide page shrunk into the top half, grey below, at every DPR. Headless records the viewport exactly. So the flow launches its own headless browser per phase (`browserType().launch({ channel: 'chrome', headless: true })`, falling back to bundled Chromium). That also keeps recording windows off the user's desktop, where closing one killed runs with `Target page, context or browser has been closed`.
15. **Rejecting a `browser_run_code_unsafe` call does not stop it.** The MCP server keeps running the code and only the result is discarded. One call that looped over 3 presets × 2 sides ran ~2 min with a blank window on screen; the user rejected it as hung, and it still recorded all six videos. Keep one call per phase, and after a rejection wait for the headless Chrome to exit before retrying, or two runs write the same webm.
16. **Record only what the dry-run walked.** A flow edited after its dry-run (landing on a sub-page instead of its parent) visited a route for the first time on camera, and the fresh worktree's Vite re-optimize crash (#4) was recorded: "Internal Server Error: Cannot read properties of null (reading 'useMemo')". Any edit means dry-run again.
17. **`showActions` prints fill values.** The action overlay renders `Fill "<value>"`, so a password typed with `locator.fill` appears in the video. Use `ui.fillSecret`, which hides the overlay around the fill.
